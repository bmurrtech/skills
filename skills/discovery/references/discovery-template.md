# Discovery map

Use in the initial meeting after at least one pain is clear enough to name.
Produce a succinct map. This is not the ranking. Do not score priority here.
If a category is obvious from their words, note it as a hint; leave confirmation
to the ranking session.

One block per distinct use case. Merge two pains when they are the same work.
Split one pain when they described different processes.

```markdown
# Discovery map — [session label]

## Read-back

[Three to six lines the facilitator can say back: the pains heard, the rough use cases, what this meeting did not decide.]

## Use cases

### [Use case title]

- **Process:** [the work to improve]
- **Pain:** [why it matters]
- **Scale:** [frequency, volume, effort, population — omit the parts not heard]
- **Value:** [the measurable improvement they care about, or "not quantified"]
- **Potential:** [AI / RPA / workflow / integration / process redesign / enablement / deterministic check / unclear]
- **Constraint:** [what they already said would block production, or "not discussed"]
- **Category hint:** [external / internal / not discussed]
- **Enterprise leverage:** [another team could reuse this / not discussed]
- **Stakeholder:**
- **Evidence confidence:** [high / medium / low] — [one clause on why]

### [Next use case, or delete]

## Parked

- [A pain that was named and is too thin to be a use case yet. Drop the section if none.]

## Out of this meeting

- Ranking
- Solution design
- Build estimates
```
